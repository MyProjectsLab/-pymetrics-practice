### M2A-01 — untimed examples, comprehension choices, and readiness boundary

Approved by the founder on 2026-09-28 in this implementation chat. This clarification governs M2A without changing either binding specification.

**Untimed examples**

- All four examples are untimed and appear in fixed order GO, NO-GO, GO, NO-GO.
- The current response starts as “withhold.” Only the first eligible press of the selected response key changes it to “press”; it cannot be undone.
- A separate “Check example” button resolves the example: GO + press is a correct response; GO + no press is a missed GO; NO-GO + no press is a correct withhold; NO-GO + press is a false alarm.
- Before checking, the only response confirmation is “Response recorded. Select Check example.” It reveals no correctness.
- While an example is active, Space must not activate Check example. Keyboard users can Tab to that button and activate it with Enter.
- After checking, show the exact approved Stop V1.1 feedback. Use “Next example” between examples and “Check my understanding” after the fourth.

**Comprehension**

Randomize the three questions, keep each question’s answer order stable, require one answer to every question, and evaluate the complete pass together. All three must be correct. An unsuccessful pass uses “Review the rule and try again. This check is not scored.” A successful pass uses “You have the rule. Next, check your device and begin the warm-up.”

| Question | Choices in fixed order | Correct choice |
|---|---|---|
| What should you do when GO appears? | “Press Space once.” / “Do nothing.” / “Press Space repeatedly.” | First |
| What should you do when NO-GO appears? | “Do nothing.” / “Press Space once.” / “Wait for it to disappear, then press.” | First |
| Can you respond after the symbol disappears? | “Yes, until the response window closes.” / “No, the symbol must still be visible.” / “Only during the warm-up.” | First |

Do not reuse one common set of answers for all questions. Retry clears all answers and returns through rule review.

- Require the explicit confirmation “I’m using a laptop or desktop with a physical keyboard.”

### M2B-02 — early-response timing anchor

Approved by the founder on 2026-09-28 in this implementation chat. This clarification resolves the overlap in Stop V1.1 Section 7.2 without changing either binding specification or the nominal 200 ms visibility, 1,000 ms deadline, or 1,200 ms interval.

1. An accepted response immediately determines and records the trial outcome and response time.
2. The stimulus remains visible until its confirmed offset, targeting 200 ms after confirmed onset.
3. The transition anchor is `max(outcome resolution timestamp, confirmed stimulus-offset timestamp)`.
4. The full 1,200 ms post-trial fixation/transition interval begins at that anchor.
5. The next stimulus is requested on the first eligible rendered frame after `transition anchor + 1,200 ms`.
6. Responses at or after confirmed offset retain resolution +1,200 ms progression. Responses before confirmed offset use confirmed offset +1,200 ms progression.
7. A fast response must never shorten stimulus visibility or create a timing anomaly merely because it occurred before 200 ms.
8. The final completion boundary uses the same transition-anchor rule. In M2B-1, this applies to the headless `batch_finished` boundary; product completion remains M2B-2 work.

With confirmed offset at onset +200 ms:

| Outcome resolution relative to onset | Next requested onset relative to current onset |
|---|---|
| Response at 99 ms | 1,400 ms |
| Response at 100 ms | 1,400 ms |
| Response at 199 ms | 1,400 ms |
| Response at 200 ms | 1,400 ms |
| Response at 350 ms | 1,550 ms |
| Timeout at 1,000 ms | 2,200 ms |

This focused correction is authorized before M2B-2. No React/browser integration, specification revision, or change to the existing anticipatory-response and genuine timing-anomaly rules is authorized by it.
