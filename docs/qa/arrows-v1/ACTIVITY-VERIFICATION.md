# Arrows V1 activity continuation — developer verification

**Date:** 2026-10-07. **Base:** `c8a8bd21697951cca953a010bdfba5e0124972e5` in isolated `/private/tmp/arrows-activity`. **Authority:** frozen Arrows V1.0 §6; specification SHA-256 `ae7360d4b81d28b23c12e265e0707934f6659fdf183c65ddac782745ad305836`. No frozen packet or candidate journey file was changed.

The Arrows root now has an optional, separate `arrows_activity_v1` continuation. Its per-session `report_viewed` events retain contiguous activity sequence, unique view ID, installation/session identity, source surface and observed wall time. A verified terminal or checkpoint snapshot must match the caller's exact expected bytes before an append. The append and root revision update occur in one IndexedDB transaction; retrying the same view ID reads the retained event rather than adding another. Authoritative readback is required after a successful or uncertain write. Opening a checkpoint report fences later changes to that review's bytes. Timed events, saved snapshots and report bytes are untouched.

Older roots with no activity field load with `legacy_absent` status and are not rewritten on read. Validation rejects unsupported activity versions, order gaps, duplicate IDs, mismatched identities and orphan journals. Individual deletion removes activity and the attempt in the same transaction; Delete all replaces the Arrows installation. Both fence late appends. Confirmed deletion emits a local and, where available, BroadcastChannel advisory notice. The UI must still reread authoritative storage. An explicit `openForDeletion()` path can identify an otherwise invalid retained Arrows root and use `deleteAll()` to replace only this game's root; ordinary `open()`, report reads and Start retain full validation.

Focused tests cover distinct views and same-ID retry, old roots, corrupt activity, exact result binding, checkpoint review, committed lost delivery, failed pre-commit write, simultaneous tab appends, delayed append after deletion, replacement, confirmation-only notices, cross-tab notice delivery, and explicit recovery from an identifiable corrupt root.
