## Logical deletion guarantee

After confirmed deletion of attempt A, every application-owned durable record contains no A choice, fairness rating, result, report, activity, raw play command, journal event, receipt identity, payload fingerprint or retained backup from which its personal result can be reconstructed. Plain serialized command strings are payloads; ordinary hashes of low-entropy amounts/ratings are also forbidden. Tests inspect field provenance and allowlisted metadata, not a global ban on numbers shared with surviving B.

Allowed retained facts about A: installation/generation, opaque attempt/ticket/request identifiers, original form ID/digest and consumed allocation ordinal, deletion identity/revision, and the minimum value-free owner/navigation fences necessary to reject stale activity. No timestamp or input/accessibility context from A is retained unless required by a separately stated live authority field. Do not retain a former result receipt identity. Form allocation stays monotonic; deleting a report never makes a consumed form unfamiliar. Delete all clears familiarity as well.

The confirmation/disclosure says: “Delete this result and its choices and ratings? Form familiarity and minimal deletion bookkeeping remain.” Confirmed deletion is logical removal from application storage and UI. It makes no promise about browser disk remnants, user exports or externally captured screenshots.

## V2 root and validation boundary

Use a typed deletion checkpoint plus a subsequent ordered command ledger. A checkpoint contains the current sanitized root facts: installation/generation/revision, lease/route, tickets/current pointers, allocation/form-exposure metadata, surviving attempts and their byte-preserved journals/reports, payload-free tombstones/retired request index, necessary value-free navigation receipts, and surviving view activity. Its header records `storage_v2_0` and the checkpoint revision. The tail ledger contains only commands after that checkpoint. No old-root backup or erased prefix remains persisted.

Retained-attempt validation metadata is separate from original attempt/event/report objects. For each surviving attempt retain the exact necessary arm/step/receipt/fairness/terminal/withdrawal inputs or equivalent independently replayable journal. This proof must derive the entire original attempt state, event sequence, revision and report. It must validate both Completed and Incomplete, all intermediate stages, form/partner/round identity, cents/rating, receipt/exposure progression, and allowed ending. A checksum or just testing `validCompleted` is insufficient. The proof is private result-bearing data and is deleted when its attempt is deleted.

Before reading a checkpoint as authority, reject unknown fields in deletion/retirement/navigation metadata and validate: schema and installation identity strings, integer generation/revision; owner/lease/route topology; ticket ownership/state and current pointers; unique attempt/request IDs; counter/form ordinal consistency; minimal exposure inventory; tombstoned attempts absent; surviving attempts independently replayable; immutable report equality to their derived committed rounds; coherent current navigation/successor; retired IDs absent from payload-bearing records. Receipt/result values must not be hidden in unrelated metadata. Complete-root equality is checked after replaying the ordered tail from the validated checkpoint with ordinary transition guards. The checkpoint proves internal consistency of retained facts, not authenticity or contents of erased history against malicious coherent database rewriting.

Every deletion transaction first validates the existing root in its actual schema. It then applies deletion, constructs and validates a sanitized checkpoint, and atomically replaces the stored root, clearing the erased tail/prefix. All stored object stores/caches containing personal attempt data must participate or be absent by design. A failed transaction commits nothing. Multiple deletions create successive validated checkpoints; no accumulation of old checkpoint copies.

## Request retirement, exact retry and navigation

Each erased play request moves to an allowlisted retirement entry `{requestId, deletionId, attemptId, generation}`. No payload, payload hash, result identity, rating/choice, event or context survives there. Reject malformed/non-opaque identity values when constructing a root; do not use arbitrary user content as an identifier.

Classify requests before mutation. A readback is nonmutating and never by itself grants current play authority. Ordered handling is:

1. A matching value-free Delete-all reset receipt may confirm its exact original request and old-to-new installation/generation boundary even after that boundary changed. Otherwise enforce the installation/generation fence. This exception cannot execute a reset again or return any old personal data. Keep only the most recent reset receipt; a later reset can make earlier confirmation unavailable, which must return fenced/unavailable without executing.
2. Retired play IDs yield typed **retired/deleted**, without mutation, data echo or display authority, for both exact and conflicting submitted bytes. This explicitly replaces V1 exact-payload/conflict discrimination after erasure: it is neither possible nor claimed.
3. Resolve existing deletion receipts and navigation receipts by the value-free canonical identity below, before rejecting their deleted origin. An exact deletion receipt confirms historical deletion despite its target tombstone; a conflicting canonical identity rejects. An exact navigation receipt confirms its saved result only. A chained command may resolve its effective successor from this validated receipt; mutation still requires the exact admitted chain, same owner/lease/generation, still-current successor and local admission/route checks. A wrong successor or unrelated chain rejects. No receipt creates a successor again or authorizes an old screen.
4. Reject fresh actions against deleted tickets/attempts. For other retained requests compare canonical payload bytes exactly and return immutable readback outcomes; conflicts reject. Apply ordinary transition guards for genuinely new permitted requests. A fresh ID targeting A cannot evade retirement.

A value-free navigation identity has ONLY `kind`, `requestId`, `installationId`, `generation`, `ownerId`, `leaseEpoch`, and kind-applicable `routeEpoch`, `ticketId`, `attemptId`, `destination`, `afterReadyRequestId`, `afterRestartRequestId`. Navigation kinds are `enter`, `ready`, `tryAgain`, `reviewReplay` and `exit`. A deletion identity has ONLY `kind`, `requestId`, `installationId`, `generation`, plus `attemptId` for individual deletion. Fields are strictly typed; optional fields have one canonical absent representation. IDs must satisfy their authority-generated format. Only applicable fields are accepted. Outcome receipts additionally allow resulting revision, origin/successor ticket, destination/resulting route and reset boundary when applicable; no choice, rating, result amounts, report, context, activity, timestamp or fingerprint thereof.

New V2 navigation/deletion commands use this canonical identity for request equality from admission onward. When an exit also ends a surviving attempt, its original event timestamp/reason remains solely in that attempt's separate replay proof/journal; deleting the attempt erases it. Retained V1 navigation/deletion receipts migrate by this exact allowlisted projection: discard `at`, runtime `input`, context and any other nonidentity payload from the receipt, without altering surviving journals/reports. This is an explicit bounded exception to V1 whole-payload equality. Migrated retry/readback compares the same projection, so differences solely in discarded fields cannot conflict or authorize/change an action; differences in any retained identity field reject. Do not describe projected receipts as byte-identical commands. Scored commands are never converted into navigation receipts and still require exact comparison while retained.

Retain a navigation receipt only while needed by a current or admitted pending successor chain. Once no current/pending chain depends on it, retire its ID and erase its body; never prune a live chain merely because its origin A was deleted. Deletion receipts remain value-free idempotent confirmations until Delete all replaces the generation. A lost deletion callback resolves through that receipt/tombstone and a fresh root read. Repeating deletion never allocates, rewrites a successor or advances revision again. The adapter distinguishes retired/deleted, fenced/unavailable, absent, rejection, corrupt storage and unknown readback; none permits endless retries or former-success display.

## Race and publication rules

- Local deletion admission immediately fences any locally displayed A facts. A delayed callback may reconcile the admitted request but cannot copy its captured payload into state/storage or restore A's display. Discard affected view/controller caches when retirement is confirmed.
- If an A write commits first, deletion erases its data. If deletion commits first, that write cannot commit or resurrect A. Applies independently to choice, receipt, fairness, terminal, report and activity.
- Terminal-first/delete-second leaves no A terminal/report payload. Delete-first/terminal-second rejects. Ordinary terminal-versus-Close/Restart precedence for a retained attempt remains unchanged.
- Deleting historical A while B is active or its callback/opening is pending preserves B, its exact records, lease/route and required navigation chain. Old snapshots cannot publish after the revision change; fresh readback can reconcile the unchanged successor. Current A deletion revokes only A's still-owned lineage.
- Try Again/Restart/Close chain receipts retain the latest admitted destination through either commit order. Unknown readback blocks new scored arm and leaves a bounded checking/manual-retry view. Timeout is never proof of successful deletion or failed write.
- Final authoritative read and synchronous UI publication share the same ordering boundary as writes, owner transfer and deletion. No await occurs after the final check. The missing-BroadcastChannel path has the same guarantees.

## Migration and old-writer fencing

Opening V2 requests IndexedDB version 2 on the same database. Upgrade is blocked visibly while an old connection remains; it must not bypass the block with a parallel database. New V2 connections close on `versionchange`. Older version-1 open requests cannot access the version-2 database. The old root must not be exposed to new play before successful schema reconciliation.

For a present V1 root, validate it with the exact historical V1 validator before conversion. Derive surviving attempt proofs from the validated command history; preserve all surviving attempt/events/context/reports and their form/event/scoring identities byte-for-byte. Purge payloads for already tombstoned attempts, not only future deletions. Keep only minimal exposure/authority metadata for those erased attempts. Write one valid V2 checkpoint/schema marker atomically, with no personal-data backup. Record migration identity in value-free metadata if needed for idempotence.

A failed or interrupted migration leaves V1 root bytes intact and blocks play until reconciliation succeeds; the IndexedDB database version may already be 2, so retry must inspect the root schema instead of treating DB version alone as completed migration. Lost completion after a committed migration is resolved by validating the existing V2 root. Multiple concurrent V2 openers share the ordered storage boundary and cannot migrate twice or overwrite a later command.

Present corrupt V1/V2, unsupported schema, missing root in an existing database, malformed checkpoint/proof or contradictory topology blocks without reset or plaintext corruption backup. Only explicit user-requested Delete all recovery may replace damaged data. New-installation absence remains distinct and initializes a V2 root only for a genuinely newly created database. Reload settles/fences an old Armed owner before new arm; it never resumes scored play. Delete all clears personal facts, checkpoints, retired IDs and familiarity, and replaces/fences the installation or increments generation so all prior callbacks fail.
