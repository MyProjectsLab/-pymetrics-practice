# Money Exchange 2 V1.0 — local authority and owner controller

Agent-authored, original storage/recovery contract. Draft, not frozen or independently passed. This changes no captured gameplay, money, forms, source claims or eligibility for public release.

## Boundary and executable evidence

The root reducer (`scripts/money-exchange-2-authority-model.mjs`) and owner controller (`scripts/money-exchange-2-owner-controller.mjs`) define one authority boundary. The reducer alone cannot establish that an input came from the current screen. The controller alone cannot establish what committed to storage. Both are required.

The executable model covers library/Instructions/Ready opening, atomic arm, admitted exit, Restart/Close precedence, lease loss/claim, deletion, terminal validation/derived report and report/Try Again handoff. It deliberately does not implement every intermediate gameplay screen or browser rendering. Those remain governed by the main specification, source-linked screen graph and production acceptance matrix. The terminal tests begin with an explicitly fixed two-round prefix; they test terminal/exit ordering and report derivation, not how the prefix was played or whether pixels were perceived. A `render_receipt` is external bounded renderer evidence checked by identity; the model cannot certify browser paint.

`scripts/money-exchange-2-authority-matrix.mjs` contains independent, fixed expected outcomes and scenarios. `check-money-exchange-2-authority-v1.mjs` executes them. The generated fixture's `authorityCases` are readable summaries of these expectations, not generated expected roots and not proof of browser qualification. Complete-record preservation and forbidden mutation assertions supplement the compact final-state oracles.

## Durable root and ownership

The full production root stores installation identity, schema/generation/revision, owner lease, route, current ticket, tickets, attempts, allocation counter/exposure history, immutable request outcomes, navigation intent and tombstones. A lease is `{ownerId, epoch, live}`. Route `{stage, epoch, ownerId}` is a capability tied to that lease. Every new play mutation validates installation, generation, current live owner and lease epoch inside the same transaction as its write. Supplying a nonempty owner ID is insufficient. Owner transfer requires ordered lease loss/recovery and a new claim; a second tab cannot reuse another tab's route. The model initial root represents a newly claimed lease at library, not implicit permission to resume an old attempt.

Tickets store generation, owner, lease epoch, state `open|consumed|canceled` and their eventual attempt ID. Attempts store immutable origin ticket, form ID/digest, owner lease, status/capability, current stage, complete round facts and immutable report. Each round retains its identity, partner/recipient, armed flag, exact decision, exposure/receipt identity, fairness and terminal. Every committed mutation increments revision. Same-request retries use exactly the same payload; conflicting reuse rejects. A recorded historical outcome is readback evidence only, never fresh play or publication permission. Delete all changes generation and fences all previous commands and displays.

## Input admission and callback isolation

There is one live owner controller per document/lease. Every mounted screen gets an opaque, private input token. Pointer, keyboard and assistive activation enter the same synchronous dispatcher with that token. A replaced token cannot admit an action. Admission assigns one immutable request ID, containing a fresh document nonce, lease identity and sequence. Duplicate activation while an action is pending creates no second command.

An accepted Close/Restart synchronously revokes the old publication epoch, shows a pending/checking destination and marks exit pending before dispatch or awaiting anything. It remains possible to Close a pending Restart. Other duplicate navigation or scored inputs remain disabled until reconciliation. No animation, read or write callback has the admission function or a current input token. Callbacks may reconcile or retry an already admitted immutable request; they cannot invent a fresh Close, Restart, Start or route opening. This is a module/controller interface restriction, not an assumption that arbitrary same-origin JavaScript is trustworthy.

## Ordered root transitions

1. **Instructions and Ready:** a current library interaction changes the route to Instructions. `ready` consumes that exact Instructions owner/epoch and opens one unarmed ticket. Try Again first validates the exact current Completed report and then opens an unarmed ticket. Neither operation allocates a form. Old route callbacks cannot use a newer route epoch. A fresh intentional library launch is a separate admitted transition.
2. **Arm:** Ready Next atomically consumes the current open ticket, allocates exactly one form/attempt with complete identity, writes its first intent and transfers root ownership to active play. There is **no separate seal operation**. This removes the interval in which saving Start and transferring control could disagree. The candidate still sees Ready/checking until authoritative readback permits the first award.
3. **Unified exit:** an admitted Close/Restart identifies its originating ticket. If the ticket is still open, cancel it without form use. If arm committed first, settle the exact attempt from that ticket, even though the root has already moved to active play. Revoke capability. Preserve a valid committed Completed report byte-for-byte; otherwise write Incomplete while preserving committed round/exposure facts and no full report. A different current ticket/attempt, tombstone, lease or generation rejects the old command. Restart atomically opens a successor **unarmed** ticket only after this settlement; Close targets library. Transaction order determines durable state, while the synchronous local exit fence prevents old pixels from being published in either order.
4. **Exit during opening:** Close can be requested while Instructions Next or report Try Again is pending. It carries that exact opening request ID, original route/ticket and owner lease. If opening committed first, Close resolves and cancels its successor ticket from the request ledger. If Close committed first, the late opening fails its old route/ticket guard. This avoids losing Close during a prearm navigation save.
5. **Close after pending Restart:** bind the exact Restart request, original ticket, owner/lease/generation, destination and resulting successor. If Restart committed first, Close operates on that current successor. If Close wins first, it cancels the original lineage and the later Restart cannot open Ready. A wrong chain rejects. An old Restart callback cannot publish after the local Close fence.
6. **Scored round writes:** the main specification's exact stage/identity guards apply. Decisions and conservative result intent commit before reveal. A bounded receipt requires an exact matching result identity. Rating/round-1 terminal precede round-2 arm. These operations cannot be admitted by callbacks from superseded views.
7. **Final terminal:** validate current capability/stage and both same-attempt/same-form round records, including receipt identity, allowed integer cents, fixed partner action when applicable, independently reconcilable totals and submitted fairness. Derive the two report pages from authoritative round bytes; never trust caller-supplied report pages. Commit round-2 fairness/terminal, Completed, revoked play capability and immutable report in one transaction. If exit committed first, reject the terminal. If terminal committed first, later admitted exit preserves all Completed/report bytes. A pending local exit prevents Test Complete/report publication regardless of callback order.
8. **Deletion, owner loss and reload:** deletion and publication use the same ordering boundary; tombstones/generation fence writes and callbacks. Individual deletion cannot remove a distinct later attempt. Lease loss settles an orphan Armed attempt and cancels an open ticket before a new owner can claim play. Reload never resumes an Armed scored session: show recovery, read and settle/fence the old attempt, then permit a new Ready. A timeout or missing callback is not evidence that a write failed.

`enter` and `ready` require the exact route epoch. Scored mutations require the applicable exact stage/revision. An admitted exit intentionally reads the latest same-lineage record inside its transaction rather than rejecting merely because arm or terminal advanced the revision. This is essential to preserving a Close requested while a write is in flight.

## Publication and readback

Every publication requires both current root authority and current local controller authority. Run authoritative readback and synchronous DOM publication inside the ordering boundary shared with deletion and owner transfer. Validate installation/generation/lease, exact current ticket/attempt/report, snapshot revision, the admitted request's recorded outcome, local screen epoch and absence of a superseding pending exit. Do not await between the final authority check and publication. A stale snapshot, unknown readback or historical request replay cannot grant display permission.

After a local exit, old arm/terminal/report callbacks may only reconcile history. They cannot clear the newer busy state or publish. A pending Restart may commit a successor before its callback; owner notifications must recognize that exact in-flight chain and retain checking, rather than discarding the pending Close or declaring the new Ready visible. The latest exit readback alone publishes its confirmed library/Ready destination.

The owner controller's test API models this synchronous boundary. Production still needs native IndexedDB/Web Lock, complete-root versus visible-state, missing BroadcastChannel, held/failed writes, lifecycle, keyboard and actual owned-renderer checks. Passing this model establishes neither those browser results nor physical accessibility qualification.

## Finite verification and scope

The executable matrix includes both root orders for arm/exit, terminal/exit, Ready-opening/Close and Restart/Close; lost callbacks and readback; stale token/T1 versus T2; wrong owner and explicit owner loss; duplicate/conflicting request bytes; wrong navigation chain; deletion before/after arm and stale reads; forged terminal; Try Again without allocation; and old-report deletion while a later attempt remains active. The 48 independent arithmetic fixtures and six original forms remain unchanged. Source fidelity, packet readiness, product developer testing, independent code audit, founder acceptance, environment qualification, mock and release remain separate.

### Pending navigation across unrelated history writes

Every ordered outcome records its resulting route identity (stage, epoch and owner). A pending owner request or explicitly chained predecessor survives an unrelated old-attempt deletion only while that exact command outcome still identifies the current route under the same generation and lease. Root revision equality is required for final read-to-view publication, not for retaining a pending request. Current-attempt deletion, successor replacement and owner/generation loss revoke the pending view. A fresh readback after unrelated deletion may reconcile the unchanged successor; an old snapshot may never publish.
