## 1. Purpose, evidence, and boundary

Digits is an original sequential recall exercise. A candidate observes one digit at a time, then enters the sequence in the same order. The fixed form provides three opportunities at each length 3 through 8; difficulty never rises or falls based on a response. This fixed design supports transparent by-length and serial-position descriptions without censoring later lengths after an error.

The private reference inventory (`ASSESSMENT_PRACTICE_REFERENCE_INVENTORY.md`, Digits section, lines 96–112) reports an individual-digit task, ordered recall, an adaptive four-digit start, three-error end, and a maximum-length report. It establishes only a familiar task family and candidate context. This design uses fixed lengths, 18 trials, separate presentation modes, original wording, a different stopping rule, independent sequences, and only descriptive scoring. No reference screenshots, audio, art, guide copy, proprietary score, trait inference, or employer claim is used. The Master Strategy requires Digits Practice, a guide-to-report journey, local history, Game 3 of its original mock, and basic outcomes including maximum recalled length, accuracy by length, serial-position errors, substitutions, and transpositions.

The candidate-facing limitation is: “This shows recall of these Assessment Practice digit sequences in this browser. It is not an intelligence, memory-capacity, employer, or hiring score. Visual and auditory runs and timing accommodations are different experiences; their results are not calibrated equivalents.” The candidate's actual invitation controls real assessment preparation. Advanced Training is unavailable for Digits in Public Beta 0.1.

## 2. Scored form and fixed assignment

`ASSESSMENT_PRACTICE_DIGITS_FORMS_V1_0.json` contains six **visual** forms `DV1`–`DV6` and six **auditory** forms `DA1`–`DA6`. Each has 18 trials in three blocks of six. Every block presents lengths **3, 4, 5, 6, 7, 8 in that order**. A complete form therefore has three trials per length and 99 target digit positions. Every trial uses distinct ASCII digits from `0`–`9`, including zero where selected. No target contains a four-digit run stepping consecutively up or down by one. All 216 sequences across the twelve forms are distinct. In each form nine digits appear ten times and one appears nine times; this is appearance balance, not a psychometric calibration. The target sequence and length are fixed by the manifest, never generated live.

Within an installation, accepted scored starts rotate `DV1` through `DV6` separately from `DA1` through `DA6`, then repeat. Standalone and mock starts share the relevant mode's counter. A durable committed arm consumes exactly one mode-specific rotation position even if no digit is later presented; an uncommitted arm consumes none. An individual deletion does not decrement a counter. Delete all replaces the installation and resets both counters. The candidate is told that a sequence or form may repeat after enough starts or after local data deletion; “unseen,” “equivalent,” and calibrated-difficulty claims are unavailable. The two presentation modes never share an aggregate report or an improvement claim.

### Reproducible constructor and identity

`scripts/generate-digits-forms.mjs` is the exact constructor. It creates forms in order `DV1`…`DV6`, then `DA1`…`DA6`. Each form's unsigned seed is `0xD1610000 + modeOffset + ordinal`, with `modeOffset=0` for visual and `0x100` for auditory and ordinal 1–6. Its xorshift32 step is `state ^= state << 13; state ^= state >>> 17; state ^= state << 5`, converting to unsigned 32-bit after each complete step. For each block and ascending length, begin with the current per-form count of digit appearances. For each slot, find the unused digits in this trial with the smallest count; choose one by `next() % tiedCount`. A candidate trial is rejected if it has a four-step ascending/descending run or duplicates a sequence already accepted anywhere in the twelve-form construction. Rejection advances the same PRNG state, does not change appearance counts, and is capped at 1,000 attempts per trial. On acceptance, increment appearance counts, add the sequence to the construction-wide set, and record one-based trial index/block/length. Failure of the cap or final balance check is fatal; there is no substitute form. The modulo choice is part of this deterministic constructor and makes **no uniform-randomness claim**.

The SHA-256 of the compact UTF-8 `JSON.stringify({version,generatorVersion,forms})` object, in that key order, is `9810f3106c7ed20efd31d11c7a012a3796bdfc2c1c72035c1bae804e38f595b1`. The JSON file carries the digest as a final property. Use exact bytes or canonical-content verification before publishing a form; a changed constructor or manifest requires a new version. `scripts/review-digits-forms.mjs` separately checks the digest and numerical constraints without importing the constructor.

## 3. Candidate journey and modes

Library → concise rule guide → two coached **untimed** examples (one three-digit visual example and one auditory-playback demonstration when audio is available) → two comprehension questions (order matters; what Submit/timeout does) → mode, input, visibility, sound and accommodation check → readiness → three scored blocks → basic report and local history. Wrong comprehension answers explain the rule and permit retry without arming. Examples never consume scored forms. Untimed guide, setup, readiness, and between-block screens have no idle timeout. Replay returns to the guide and receives the next durable form in the selected mode.

The candidate chooses exactly one scored presentation mode before Start:

* **Visual:** one large high-contrast digit is displayed at a time. The actual digit is hidden from assistive-technology text during scored presentation; a screen reader must not reveal the answer. The guide and entry remain accessible. State plainly before Start that nonvisual interpretation of this visual form is unsupported in this beta.
* **Auditory:** one English digit word is queued at a time through the browser's `SpeechSynthesisUtterance` API. An eligible voice is a current `speechSynthesis.getVoices()` entry with nonempty `voiceURI`, BCP-47 English `lang` (`en` or `en-` followed by subtags, case-insensitive), `localService === true`, and a `voiceURI` that occurs exactly once in the current inventory. Missing/unknown/false `localService`, remote voices and ambiguous duplicate URIs are ineligible. Both explicit choice and default choice are restricted to this eligible set: an explicit ineligible URI is rejected without automatic substitution; with no explicit choice, choose the eligible voice with lexicographically smallest `voiceURI`. Assign the verified voice object to every sample and scored utterance. Before arming, the candidate must play two unscored sample digits with that voice, browser start/end callbacks must arrive, and the candidate must affirm that both were audible. Freeze its `{voiceURI, lang, localService: true}` identity, rate `1.0`, pitch `1.0`, and browser speech capability in the profile. Re-enumerate and require exactly the same eligible URI/language/local-service identity before the samples, accepted arm/Start, every Continue and each scored utterance request, and at every sample/scored start/end callback; also recheck that the assigned utterance voice is the selected eligible voice. If the selected voice disappears, becomes remote/ambiguous, changes language/identity, or the voice inventory cannot be verified, disable auditory Start/Continue before protection and invalidate an already armed or protected attempt as a voice/profile failure. Missing callbacks, failed samples or declined audibility also disable auditory Start. If no eligible local English voice exists, auditory mode is unavailable with an explanation; visual Practice remains selectable and usable. Never silently switch an auditory attempt to visual or another voice. No target digits are placed in DOM text during auditory playback. Browser callbacks are observations of the speech engine, **not verified acoustic onset**; playback/device differences are disclosed and auditory results are separately labeled. Screen-reader and TTS interaction needs browser/device qualification before calling this mode supported on a particular setup.

Visual stimuli are the manifest's ASCII digits rendered with original application layout/CSS and system text fonts. The packet includes no copied image or audio asset. Auditory speech uses a browser-provided voice at runtime; the application distributes no voice recording. The spoken digit words are ordinary number names. Any future bundled recording or changed speech method requires its own rights/provenance record and a new versioned presentation contract before use.

The entry control is one labeled text field with `inputmode="numeric"`, a visible numeric keypad, `maxlength` equal to the current target length, and a separate Submit and Skip button. It accepts only ASCII `0`–`9`; a response may contain zero through the target number of digits, with no separator or leading-zero removal. Setup chooses **keyboard text entry** or **keypad entry**; only that numeric-entry path is active during a scored attempt, while accessible Submit/Skip activation remains available in either. Keyboard entry accepts physical digit keys and supported assistive output as ordinary text input; keypad entry accepts pointer/touch or assistive button activation. Clicking to focus the text field is not a change of entry method. Sanitization occurs before acceptance; non-digit and excess input is rejected with a message, without recording the rejected character. Paste/drop/autofill that produces accepted digits is allowed but records `assisted_entry=true` and is labeled separately in the report and history; no anti-cheating claim is made. Composition remains uncommitted until `compositionend` and sanitization. Enter activates Submit only from the input or Submit button; Space/Enter keep normal untimed button semantics. During playback, the input is unavailable. Focus moves to the untimed heading, then to the entry field or first keypad button when entry opens. An accessible countdown announces remaining time at 10, 5, and 0 seconds only; it must not read each rapidly changing second or disclose hidden targets. Library metadata describes visual Practice as **about 3–6 minutes plus untimed breaks**; the fixed visual presentation accounts for about 1.7 minutes before browser frames and responses. Auditory duration depends on the selected speech engine and is described as variable.

The setup freezes `{mode, entryWindow, highContrast, reducedMotion, entryMethod, assistedEntryDeclared, voiceURI, voiceLang and localService=true if auditory}` at the accepted arm and shows it at every break and report. Standard entry window is 20,000 ms; a selectable **extended-entry** accommodation is 35,000 ms. Its report is labeled “extended entry” and never silently compared with standard timing. High contrast is available in both modes; reduced motion removes nonessential animation. A candidate may change setup before Start. In-app changes after Start are locked; a detected profile change during a protected block or break invalidates the attempt and requires a new arm. Browser zoom at a break is allowed only if the visual-layout check still passes. The selected mode does not change mid-attempt.

## 4. Trial schedule, input boundary, and validity

Use `performance.now()` as one monotonic clock within a document. Record a new clock-domain ID after reload; never subtract times from different domains. An accepted Start/Continue first proves exclusive live-run ownership, current installation/arm, storage availability, visible/focused document, profile, and layout. Start is accepted only after an atomic arm plus authoritative readback; Continue only after the prior block's complete known prefix is authoritatively checkpointed and current ownership/profile is rechecked. Each block starts on an explicit candidate action. The first presentation begins only after a connected visible placeholder is confirmed on an animation frame.

**Visual schedule.** Write digit 1, confirm its connected visible display on an animation frame, and record `digit_onset_ms`. The digit remains through `onset+700 ms`; request removal at that deadline and confirm absence on a frame, recording `digit_offset_ms`. For digits 2…N, the next write is due at the prior confirmed offset + 250 ms. After the final confirmed offset, entry opening is due 750 ms later and is confirmed on a frame. All deadlines are based on observed confirmations, never backdated to scheduled times. A callback before its due time waits. No full sequence, future digit, or answer appears in the DOM during playback.

**Auditory schedule.** Queue only one utterance at a time with the English word for the current digit, after the selected local voice passes the current-inventory identity check. Record handler time on `onstart` and `onend`, the voice URI/language/local-service identity, and the digit index. Start the next utterance no sooner than 250 ms after the previous observed end; open entry no sooner than 750 ms after the last observed end. The speech engine may vary actual duration and audible onset, so there is no visual/auditory pacing-equivalence claim and no cross-mode response-time comparison. If an utterance lacks `onstart` within 2,000 ms of its request, lacks `onend` within 4,000 ms of observed start, errors, is interrupted, or reports a changed voice, invalidate. Cancel queued speech on invalidation/exit; a late callback cannot add an onset or complete a trial.

Entry starts at a confirmed `entryOpenedMs`; its deadline is `entryOpenedMs + 20,000` or `+35,000`. Every eligible edit handler samples the monotonic clock; edits before entry opening or at/after the deadline are ignored, so a delayed deadline callback cannot admit late digits. A Submit handler at `entryOpenedMs <= submitMs < deadlineMs` commits the then-sanitized eligible value once. Skip at a handler time before the deadline commits the empty string with `skipped=true`. At the exact deadline or later, the deadline handler commits the last eligible value as **timed out**; late Submit/Skip actions cannot replace it. Each trial closes once after that commit; it is exact-correct only when an **on-time Submit** committed the target string. A timed-out full matching draft is still scored wrong and labeled “full entry present at timeout”; its position-string matches remain factual. An empty, partial, skipped, or timed-out answer is not an unpresented trial. Keep the entry screen visible until its commit. No trial feedback or target reveal appears during a scored block. At each six-trial boundary show exact-correct, wrong, skipped and timed-out counts for that block, then require explicit Continue. No trailing presentation follows block 3.

Visual stage lateness and foreground frame gap are measured at handler/frame time against their own due times. A visual confirmation or offset lateness **>250 ms**, or protected foreground frame gap **>250 ms**, invalidates; exactly 250 ms is a non-severe quality note. Greater than 50 through 250 ms records a timing/presentation note. A required visual frame absent at its original due+2,000 ms has an independently scheduled watchdog; invalidate on the first runnable check at or after that point. A confirmed digit presentation is recorded before an immediate lateness invalidation, including when the frame-gap monitor and a due presentation confirmation run in the same frame; canceled pre-onset work creates no exposure. An auditory callback timeout or lifecycle failure invalidates as above. Do not equate a browser event with verified acoustic delivery. The response window is never silently extended by a delayed callback; it begins at actual confirmed entry opening. Input resolution and display callbacks never await storage.

The protected period starts at accepted block Start/Continue and ends after the block's sixth trial closure or invalidation. Hide, blur, freeze, page exit, layout failure, unsupported input/profile change, voice failure, ownership loss, and severe timing failure during protection invalidate and leave an in-tab review-only draft. Hide during guide/readiness/break does not itself invalidate, but Continue rechecks admission. The applicable footprint (future digit, progress and entry control at admission; actual digit/entry during play) must be mounted, visible, unobstructed by an app overlay, inside the layout width and visual viewport, with no horizontal overflow or timed-play scroll, including at 200% zoom on the supported desktop viewport. Before protection, failed admission explains how to resize/zoom and allows recheck. During protection it invalidates. A 320-pixel responsive check is development evidence, not blanket mobile qualification.

The scored state machine is `armed → presentation → entry → trial_closed`; each of trials 1–17 either returns to presentation or enters an untimed `break` after trials 6 and 12, and trial 18 reaches `completed`. `break → presentation` requires a confirmed checkpoint and explicit Continue. Any protected state can reach `invalid`; a page reload of nonterminal durable state is shown as `incomplete` without invoking a scored transition. At most one current trial, one presentation stage, one response commit and one trial close exist at a time. An epoch/request token fences every frame, timer, speech callback and storage delivery, so a canceled callback cannot advance the state or append an event.

## 5. Versioned journal, storage, and recovery

Versions are `digits_spec_v1_0`, `digits_forms_v1_0`, `digits_constructor_v1_0`, `digits_timing_v1_0`, `digits_input_v1_0`, `digits_event_v1_0`, `digits_storage_v1_0`, and `digits_scoring_v1_0`. An attempt records installation/session/mock identities, mode/form and manifest digest, start request ID, profile, clock-domain ID, contiguous event sequence, one-based block/trial/digit indexes, command and event times, and all known presentation/response facts. Every event has `{schemaVersion, installationId, sessionId, formId, clockDomainId, sequenceNumber, block, trialIndex, atMs, type, detail}`. Sequence numbers start at 1 and are contiguous; times never regress in one clock domain. `prepared`, `form_assigned` and `armed` form the durable initial prefix; `armed` and each `block_continued` record the full frozen profile. The mode-specific timed event details are:

| Event | Required detail |
|---|---|
| `block_started` | Block number and accepted start time. |
| `digit_presented` / `digit_ended` (visual) | Digit index/value; due, actual confirmation and lateness milliseconds; the ended event confirms the digit is absent. |
| `speech_started` / `speech_ended` (auditory) | Digit index/value; speech request/start/end handler times and selected local voice URI/language/`localService=true`; these are browser observations. |
| `entry_opened` | Actual confirmed opening, deadline, entry-window version. |
| `answer_committed` | Final sanitized string, handler time, entry source class, `skipped`, `timedOut`, `assistedEntry`; exactly one per closed trial. |
| `trial_closed` | Target length, exact-correct Boolean and derived position-accounting fields, verified against target/answer events. |
| `block_summary_ready` / `block_continued` | Block identity, six-trial counts; continuation also carries the frozen profile and new protected start time. |
| `quality_note` / `invalidated` / `session_completed` | Stage/reason and observed time; terminal events occur at most once. |

`block_summary_ready` ends protection. The confirmed checkpoint revision is storage metadata, not a backdated timed event; `block_continued` is appended only after its authoritative readback. Do not record unrelated raw keys, rejected non-digit characters, personal identity, or employer identity. Browser event timestamps are not substituted for handler-observed monotonic times. Store a versioned derived result snapshot only when it exactly reconciles with the immutable event journal; changing scoring requires a new scoring version and never silently rewrites historical results.

The Start request acquires one exclusive Digits browser owner, then uses one IndexedDB read-write transaction on the installation root: verify installation/schema, allocate the next form from the selected mode counter, increment exactly that counter once, and insert an armed attempt with the initial ordered journal prefix. The commit **and authoritative readback of the exact request/attempt/counter** are necessary before timing or presentation. A rejected arm does not consume a count. If commit succeeds but callback delivery fails, readback with the same request ID recovers without double allocation. If readback is unavailable, show “Start could not be confirmed” and do not start. A pending acquisition/readback can be canceled and must release ownership; late callbacks cannot start a canceled run. Storage failure disables scored Start; no unlabeled temporary run is offered.

Keep events synchronously in memory. At each untimed block summary, checkpoint the complete known prefix, closed-trial count and frozen profile under an expected revision, then authoritatively verify it before enabling Continue. A failed or indefinitely pending delivery can be read back and retried for the **same immutable prefix** while untimed. Explicit End at a break captures that known prefix before releasing ownership; it is an **Incomplete/review-only** draft, not a completed terminal result. Attempt an out-of-timing checkpoint after release and allow readback/retry of the exact prefix, with no durable saved claim until verified. If that remains uncertain, retain the in-tab draft and disclose that only the last committed prefix is recoverable. At invalidation or completed terminal state, copy the immutable state first, release ownership, then save/read back the exact terminal bytes; failed or undelivered writes retain a truthful in-tab draft and same-byte retry.

A reload never resumes playback, entry, or a between-block break. An armed/checkpoint attempt without a terminal event is Incomplete; a new accepted arm restarts from trial 1 using the next form. A mid-block crash may lose events after the last checkpoint, including actual sensory exposure. History labels the saved prefix “later presentation status unknown,” never zero exposure or a completed score. A confirmed digit onset remains in memory even when invalidation occurs in that callback; a canceled pre-onset callback creates no exposure. Each transactional write/readback rechecks installation ID, exact arm identity, expected revision, and session tombstone. Individual deletion removes attempt/result/activity and writes a tombstone without decrementing counters. Delete all atomically replaces the Digits installation, resets both counters, and removes all Digits records; other games are untouched. Delayed saves, retries, report-view appends and notices cannot resurrect a deleted attempt or write into a replacement installation. Saved reports are opened from fresh authoritative reads; cross-tab deletion withdraws stale saved claims promptly, and absent notices never authorize a new saved claim.

Form exposure is tracked at two different strengths: an accepted durable arm consumes its mode rotation position, while the first confirmed digit event is observed presentation of that trial. Neither an arm alone nor an incomplete saved prefix proves that later digits were unseen. No report or replay copy may infer zero exposure from missing post-checkpoint events.

Every genuine opening of a verified result appends a separate versioned `report_viewed` activity event with a fresh view ID, wall-clock time and source surface. A retry of that opening reuses its ID and is idempotent; the append checks exact result identity and deletion authority. Activity never changes timed journal bytes or recall scoring.

## 6. Reconciliation, scoring, and basic report

For every attempt, `presentedTrials = closedTrials + unresolvedPresentedTrials` and `18 = presentedTrials + unpresentedTrials`. A trial becomes presented when its first digit onset is confirmed (visual) or first speech-start callback is observed (auditory). A partly played sequence is presented but unresolved; it is **not** wrong or omitted until `answer_committed` and `trial_closed` exist. A complete valid attempt has exactly 18 presented/closed trials, 3 block boundaries, one committed response per trial, exact form identity, no invalidation, and `exactCorrect + wrong = 18`. Any invalidation suppresses all aggregate accuracy and error tables, even if 18 closures later appear. A reload without a terminal event is Incomplete. Invalid/Incomplete review shows only status/reason, presented/closed/unresolved/unpresented counts, factual ordered events/known responses and a warning that later display after the durable prefix may be unknown.

For a **Valid** attempt, `maximumRecalledLength` is the greatest length among on-time exact Submits, or “No sequence recalled exactly” if none. Accuracy by length is exact recalls out of 3. Overall exact count is out of 18; each block count is out of 6. Skip and timeout counts are factual overlapping subsets of wrong. Percentages are computed from integer counts and rounded half-up to one decimal. Never use a maximum **attempted** length as a recalled length.

Serial-position analysis treats the committed answer as an ordered string aligned from its first character. Its length is at most target length. For a **full-length** answer, scan positions left to right: a correct digit is a position match; when two adjacent as-yet-unclassified response digits equal the reversed target pair, classify one disjoint adjacent transposition pair and mark both positions; every other entered mismatch is a substitution. For a **partial** answer, classify each entered position as match or substitution; transposition detection is disabled, and absent trailing positions are `missingSuffix`. Thus for each closed trial: `targetLength = positionMatches + substitutions + 2×transpositionPairs + missingSuffix`. “Substitution” and “transposition” here describe string differences, not the mental cause of an error. An input with a nonadjacent move is counted as position mismatches, not speculatively inferred as a swap. A skip has `missingSuffix=targetLength`.

The report shows mismatches by serial position with denominators `[18,18,18,15,12,9,6,3]` for positions 1–8 in any complete form. An error position includes substitution, either position of a classified transposition, or missing suffix. It also shows total substitutions, disjoint adjacent transposition pairs, and missing-suffix positions, alongside the 99-position conservation identity. A full matching string at timeout has zero position errors but remains a scored wrong trial; show this distinction rather than hiding it. The report distinguishes visual/auditory, standard/extended entry, assisted entry, high contrast, reduced motion, voice identity where applicable, browser/device context, presentation-quality note count and interruption. It gives a short task-limited observation such as “You recalled 2 of 3 five-digit sequences exactly; position 5 differed in 1 of its 12 opportunities.” No latent trait, improvement classifier, normative percentile, pass threshold, employer fit, or hiring prediction appears. The report includes Replay, local history, the limitation in §1, and “Advanced Training is not available for Digits in this beta.” Auditory performance is reported separately from visual and is not described as equivalent. An accommodated or assisted run is labeled and never silently pooled with standard runs.

History records mode/form, repeat ordinal, valid/invalid/incomplete, accommodation/assisted-entry label, time, and saved status. Opening any retained report revalidates the exact manifest, event order, phase transitions, timing feasibility, snapshot revision, profile, and deletion authority; a malformed or unsupported historical version remains review-only, never silently rescored. Clearing local data also clears form-exposure history; the interface says so.
