## 2. Candidate journey and clocks

1. Guide explains two-minute run, 5-second decisions, 5/3 Easy, 60/12 Hard, stated payout chance, and motor demand. A coached Easy example and two-question comprehension check precede the scored attempt. They do not consume a form or enter the report.
2. The ready screen shows the input, sound/motion options and a single **Next** control. Before showing the first scored offer, acquire exclusive attempt ownership, reserve an unseen form durably and verify visibility. The scored clock starts when the first offer is confirmed visible after Next. If visibility cannot be confirmed, do not claim a valid start.
3. Each offer shows common payout chance, Easy 100 cents, Hard amount, current earnings and two adjacent labeled controls. Candidate selects one. The choice clock is 5,000 ms from confirmed offer onset. If no eligible selection has a native event timestamp strictly before its deadline, the offer's fixed fallback task is selected and marked `automatic` in the journal. A timely selection remains eligible when its durable write completes after the deadline; timeout resolution waits for that pending write/readback. The selected control is visually distinct and remains labeled; color alone is insufficient.
4. The task screen shows choice, chance, amount, current earnings, remaining task time and a single central progress bar. The task clock starts at confirmed task onset. Standard input is one physical Space press and release per pump; a press is timestamped at its matching keyup, so a release at or after a deadline does not count. Held-key repeat, overlapping downs, synthetic script events and a key held across onset produce no presses. The fifth Easy or sixtieth Hard eligible press strictly before both its task and global deadlines completes the task. Partial fill reflects committed counts only. Input at or after a deadline is ignored.
5. When timely completion occurs, compare the form's hidden basis-point draw against `probabilityPercent × 100` (strictly less). A win pays the selected amount; a loss pays zero. A timed-out task always pays zero, independent of the hidden draw. Complete, lottery loss and task timeout receive plainly distinct feedback. Feedback auto-advances after **4,000 ms**, provided the game clock remains. Feedback duration counts within the 120 seconds. This approximate dwell is an original choice within the captured feedback-to-next-choice interval; it is not claimed to be the provider's exact duration.
6. All scored windows are half-open: an action is timely only when its native handler timestamp is strictly less than both its phase deadline and the global 120,000-ms deadline. At an exact tie, the deadline wins regardless of callback or transaction arrival order. At global expiry during an unfinished task, record that task incomplete with zero payout. At global expiry during a choice with no earlier eligible selection, add no task. If a choice was captured before global expiry but its durable confirmation or task display occurs after expiry, keep that choice in the ordered journal and choice totals, append a `global_expired_after_choice` terminal event at elapsed 120,000 ms, and add no task attempt, task row, completion or payout. If readback proves the choice did not commit, append ordinary `global_expired_in_choice` and do not count the choice. The task is never displayed after expiry. A previously captured eligible action must be resolved durably before timeout or terminal result publication. Finish at the global deadline and display the report only after terminal storage is verified.

Use one monotonic browser clock for the running attempt; persist wall-clock anchors for suspension checks, not for optimistic resumption. Every timer callback rechecks the current monotonic time and attempt identity before changing state. Never extend a deadline because a callback was delayed. If document hiding, page lifecycle suspension, lost ownership or material clock uncertainty occurs during scored play, stop the attempt as interrupted and label it review-only; no mid-game resume. The next valid attempt uses a fresh form. The timed task never pauses except before Next.

## 3. Forms, assignment and outcome authority

The four draft scored forms are `EH1`–`EH4`, each with **512** indexed offers. This inventory length is implementation capacity, not a candidate-visible trial count. At the required 4,000-ms feedback dwell, 512 tasks cannot be exhausted inside 120 seconds. Every entry fixes the common chance, Hard amount, hidden fallback direction and hidden lottery draw. For zero-based generator index `i`, field `f`, and form `EHn`, the generator hashes the UTF-8 bytes of `Assessment Practice|Easy or Hard|V1.0|EHn|i|f`, interprets the first eight digest bytes as an unsigned big-endian integer, and reduces it modulo the applicable support size. The fields are `probability`, `hard-reward`, `fallback`, and `lottery`. The EH1 opening Hard amount alone is set to 124 cents to match the captured first visible offer (88%/$1.24); its hidden fallback/draw remain generated. Other offer order and hidden outcomes are original. The JSON bytes and SHA-256 are published with the packet. There is no runtime RNG dependency.

Candidate-facing report data excludes hidden draws and future offers.

Normative arithmetic examples from EH1 (the hidden draws are audit values, never shown in the candidate report): offer 1 has 88% chance, Hard 124 cents and draw 4836, so timely Easy earns 100 cents and timely Hard earns 124 cents. A five-second choice timeout on EH1 offer 1 automatically chooses Hard; it is recorded as an automatic choice, not a task failure. At global expiry during a choice, that unselected offer creates no task attempt.

## 4. State, events and action contract

Phases: `guide → example → check → ready → choice → task → feedback → choice … → complete`; `interrupted` and `unconfirmed_save` are separate terminal/recovery states. Every scored journal event has `eventVersion`, `attemptId`, `formId`, `formHash`, `ownershipGeneration`, unique monotonically increasing `sequence`, `kind`, `phase`, monotonic `elapsedMs`, `wallTimestampMs` and `inputSource`. Offer-scoped events also have `offerIndex`. The normative payload is **event-specific**; outcome fields are required on resolution, not on every press:

| Kind | Additional required fields |
|---|---|
| `offer_onset` | `probabilityPercent`, `easyOfferCents`, `hardOfferCents`, `choiceDeadlineMs` |
| `choice_selected` | unique `actionId`, `choice`, `automatic` |
| `task_onset` | `choice`, `automatic`, `probabilityPercent`, `selectedRewardCents`, confirmed `taskOnsetMs`, `taskDeadlineMs`, `acceptedPresses: 0` |
| `press_accepted` | unique `actionId`, native `pressId`, `choice`, `taskOnsetMs`, `taskDeadlineMs`, new `acceptedPresses` |
| `task_resolved` | `choice`, `probabilityPercent`, `selectedRewardCents`, `taskOnsetMs`, `taskDeadlineMs`, final `acceptedPresses`, `completedOnTime`, `lotteryWon` (`null` when incomplete), `earnedCents`, `reason` |
| `feedback_end` | No additional payload beyond the common fields and `offerIndex` |
| `global_expired` | Terminal `phase`; no offer index when expiry occurs in feedback or a fresh choice |

The replay fixture's `expectedJournal` is the exact field-and-value oracle for its ideal-confirmation trace. The shorter `expectedJournalFragment` arrays in deadline cases assert only the listed fields, with the same event-specific schema applying to any complete implementation journal. An `actionId` is generated by the app at the native action, committed once, and cannot be reused within an attempt. Hidden lottery draws and future offers never enter candidate-facing report data.

Native trusted button click activates a choice once. An app-owned activation token is created on entry and committed with the choice so duplicate click/Enter/Space activations cannot choose twice; keyboard focus changes do not reset it. Native physical Space `keydown` with `repeat=false` and a matching `keyup` is one press while the task owns focus. Ignore presses from text inputs, modifiers, composition, unrelated focused controls and untrusted programmatic events. Serialized press/choice/timeout actions and durable commits have one order; deadline decisions use captured native timestamps and the half-open precedence rule above. Focus is moved to the task instruction/progress on task onset, to a concise feedback status on resolution, and to the next choice when it appears. Live announcements are polite and do not announce every press.

An explicitly remapped input or pointer/touch accommodation uses the same visible task and separately labeled **accommodated input** report context. It is not compared as equivalent to standard keyboard motor demand. Provide a visible countdown and progress text as well as fill; reduced motion removes nonessential animation. Accessibility changes during a scored task invalidate the attempt rather than silently changing conditions. Screen-reader users can review instructions and results; the timed motor task's nonvisual limitations are disclosed.

## 5. Storage, recovery and deletion

Use local IndexedDB authoritative root records and exclusive same-browser attempt ownership. `Next`, each choice, each accepted press, each resolution and terminal result are serialized durable writes. At the start of each trusted native handler, capture `performance.now()` synchronously; do not trust a caller-supplied or script-set `Event.timeStamp`. Enqueue the action in one attempt order using that captured monotonic timestamp. Every timeout is an action with its fixed deadline timestamp; it cannot overtake an earlier captured eligible action. At equal timestamps the timeout has priority. A transaction compares the current root revision and commits the winning transition; until confirmation/readback, the view remains in checking-save state and cannot display a fallback, next phase or report. Storage latency never changes captured eligibility, but an action cannot be credited or displayed as authoritative until its durable write is verified. Failed or undelivered writes require readback of the action identity before the queued timeout can settle. A stale callback cannot restore an earlier phase, result or eligibility after deletion/replacement.

Both individual deletion and Delete all retire the exact attempt and its journals, summaries, report-view activity, exposure record and relevant ownership. Deletion and replacement have a shared ordering boundary with Next and result publication. A read that started before deletion cannot publish a saved result afterward. Cross-tab notifications improve promptness but are not the authority; reads and writes check current root revision. If the browser cannot provide durable storage or exclusive ownership, the scored simulation does not start. Uncertain terminal delivery cannot be reported as saved; verify it or offer recovery from history.

## 6. Report and integration

The report shows: form/scoring version, complete/invalid/interrupted status, elapsed time, task attempts, on-time completions and rate, Easy/Hard choices and automatic choices, Easy/Hard completion rates, each offer's stated chance and amount, actual earned cents, aggregate earnings, task durations and input/accessibility context. Choice totals count committed selections, including a last choice made before expiry whose task never appeared; task attempts count only confirmed task onsets. The report labels such a last choice as **selected as time expired; task not started**, without a task row. Overall completion rate is completed tasks divided by attempted tasks; Easy/Hard rates use their own attempted-task denominators. If a denominator is zero, show insufficient evidence rather than a numeric rate. A choice window ended by the global clock adds no task attempt. A task row distinguishes completion from payout; a timely completed losing draw is not a timeout. Durations render `mm:ss` using floor of elapsed whole seconds, with source milliseconds retained. Show an original practical observation such as which selected task type had more timely completions, only when sample size is sufficient, and do not prescribe personality or employer behavior. Show independence and lottery/form-difficulty limits.

History reopens the same reconciled result after reload. Replay starts a new versioned attempt. Full mock uses this game as Game 9 in the original Assessment Practice order and follows the same no-midgame-resume rule; a mock interruption restarts this game on a fresh form where available. Do not add an employer score, rank, pass/fail, Advanced Training or optional analytics to V1.0.
